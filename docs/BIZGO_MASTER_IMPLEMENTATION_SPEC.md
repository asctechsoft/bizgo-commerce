## 00. Executive goals and implementation boundaries
- BizGo is **single-seller direct commerce**; family/partner factory is supplier/fulfillment partner, NOT a seller marketplace. No seller self-service, multi-vendor settlements, marketplace commission or public factory profit access.
- Channels: B2C retail, B2B verified wholesale; later Flutter app with the **same** API and business rules.
- Customer web and admin/factory are distinct role-scoped experiences backed by one modular monolith API; workers handle background tasks. No microservices for initial MVP.
- The supplied HTML/CSS/JS prototype defines **visual and functional intent only**. It is a localStorage demo, not security, pricing, production checkout or backend truth. Recreate it as reusable Next.js components and real API calls. Do not ship hard-coded OTP (`123456`), fake checkout success, fake payment, mock tier prices, autogenerated order IDs or demo browser storage as production logic.
- MVP goal: search genuine sellable SKUs → server quote → idempotent order → BizGo confirms → scoped factory picking/packing → shipment → financial reconciliation with auditable trail. Customer can track and receive help; unsupported SKU stays draft.

**Invariants:**
1. Currency VND integer in minor units or PostgreSQL numeric exact, one convention globally; order line snapshots contain SKU name, pack metadata, unit price, discount allocation, tax status and supplier cost at order acceptance time. Cost snapshot fields encrypted/permissioned as needed and not sent to customers.
2. Balances keyed by `(warehouse_id, variant_id)`; use ledger and constrained transactions so `on_hand >= 0`, `reserved >=0`, `quarantined >= 0`, `on_hand >= reserved+quarantined` when applicable. Reservations hold physical on_hand; dispatch reduces physical and releases reserved **exactly once**.
3. Lot assignment follows applicable FEFO policy with expiry/quality checks. Do not promise lot/HSD field availability for items where not applicable; still track source/batch as policy requires.
4. Every financially sensitive or state-changing mutation writes audit and outbox in same database transaction; outbox consumer retry may duplicate delivery, so handlers must be idempotent.
5. `idempotency_keys` unique by actor/scope/key with request hash+response snapshot/TTL; client retry with same key and changed body must fail safely.
6. Orders, payments, shipments and returns maintain separate status enums; no single boolean `isPaid` controlling all actions. Payment receivable and cash settlement are independent.
7. PII and private media access is authorized; use soft delete/redaction/retention compliant with reviewed policy, not cascading delete of financial ledger.
8. Use UUID/ULID internal IDs and readable public order numbers; never trust public ID alone for tracking.
9. DB FK/index plan: product slug, sku unique, category_id/status, org/tier price lookup, order customer/created/status, stock `(warehouse,sku)`, lots expiry, idempotency unique, external provider event unique, outbox pending index.
10. Sample migrations must be reversibility-aware; no reset/migrate dev against production, no destructive schema changes without reviewed migration plan.

## 07. End-to-end flows and backend transaction sequences
### FLOW A — B2C catalog → COD/transfer order
1. Public catalog returns only eligible listing/SKU availability. PDP selection triggers server price/availability response.
2. Guest/customer adds SKU qty to cart. Cart persists via server/session; any cart totals are informational, not final.
3. `POST /v1/checkout/quote`: validate actor, contact/address, destination, variant publication, min/max quantity, storage class, carrier/region, promotion; compute exact line totals, discount, applicable tax policy, shipping estimate. Return quote ID/version/TTL, line snapshots, blocked reasons. If carrier pricing undecided, do not fabricate rate; require manual quote or prevent checkout based on configured policy.
4. Client confirms quote and sends `POST /v1/orders` with `Idempotency-Key`, quote ID/version and accepted totals; backend recalculates/revalidates and rejects changed quote with `PRICE_CHANGED`/`OUT_OF_STOCK`/`DELIVERY_UNSUPPORTED`.
5. In one PostgreSQL transaction, atomically reserve qualified stock, create order+line snapshots, payment record `PENDING`, order events, idempotency record and transactional outbox. Concurrency 2 buyers / stock 1 yields 1 successful reservation, 1 conflict.
6. COD order is **not paid** at creation. Manual bank transfer creates `AWAITING_VERIFICATION`; finance matches amount/reference and records actor/evidence. No client-confirmed paid state.
7. Sales/BizGo confirms policy+address+fraud check, creates factory fulfillment assignment. Factory scoped worker accepts, confirms lot, picks, packs, uploads evidence, marks ready; system can create manual shipment/tracking.
8. Carrier shipment lifecycle and delivery evidence updates shipment, not instantly cash. COD remains receivable until reconciled and credited. Stock dispatch booked once on handover/approved warehouse transfer.
9. Finance matches carrier COD remittance and supplier costs/fees/refunds, closes expected vs actual margin and settlement. Notifications are jobs, never inside checkout transaction.
10. Cancel paths: before dispatch release reservations; after dispatch operate return/recall and reverse logistics; captured payments refund through controlled workflow.

### FLOW B — B2B application → tier quote → order
1. Authenticated customer submits business profile, relevant tax/registration details only when required; status `SUBMITTED/UNDER_REVIEW`.
2. Sales/owner reviews with audit and approves organization+tier; denial and reapplication reason visible. Unapproved users cannot access privileged tier-price API.
3. Approved customer sees tier price only for own org; MOQ, pricing validity and delivery restrictions checked server-side.
4. Standard B2B cart follows A; large/variable quantity uses quote request. Sales enters sourced supplier cost, transport/production dates and expiration, seeks approval for discounts exceeding permission limits.
5. Customer accepts an unexpired quote; order is created idempotently using immutable approved quote snapshot. Deposits/credit limits supported only after explicit owner/accounting decision; default disabled.
6. Partial fulfillment/shipment and accounts receivable/cost settlement accounted per parcel; reorder creates new quote and revalidates today's price.

### FLOW C — Stock shortfall, factory exception, partial order
1. Factory can report `SHORTAGE`, `QUALITY_HOLD`, `LOT_EXPIRED` with reason/evidence; cannot silently swap SKU.
2. Sales offers wait/produce, substitution with explicit customer acceptance, split shipment, cancel and refund; any changed line price/ship schedule needs customer acknowledgement.
3. Reservation release/reallocation and money adjustments are atomic, idempotent and fully audited; no artificial positive stock.
4. Partial pick/pack/ship tracks line and parcel quantities; do not mark order completed before all fulfillments/approved adjustments are accounted.

### FLOW D — Return/refund/complaint
1. Authenticated order owner or verified guest submits case with reason, timestamps and private signed photo uploads.
2. CS reviews delivery, lot evidence, cause and eligibility based on approved policy; factory verifies assigned batch only; accountant approves monetary action if needed.
3. Return labels / replacement / refund chosen by authorized role; stock is restocked only after inspection. Refund references original payment where applicable and retains provider reconciliation.
4. Adjust margin, supplier payable, claim responsibility and audit without deleting historical order values.

### FLOW E — Admin/factory daily operations
Admin: queue & SLA → verify → factory assign → packing progress → shipping tracking → customer updates → COD/payment mismatch → reconciliation → report. Factory: assigned queue → accept → confirm stock/lot → pick → pack/count/weigh/photo → handover → historical job, **without finance fields**. Daily checks: failed jobs, holds, expired lots, overdue refunds, stock anomalies, unremitted COD.

## 08. State machines and transition guards
Do not copy status verbatim as authoritative if product owner changes workflow; implement explicit transition service, not uncontrolled PATCH status.

**Order:** `DRAFT_QUOTE → PENDING_PAYMENT_OR_CONFIRMATION → CONFIRMED → FULFILLING → PARTIALLY_SHIPPED / SHIPPED → DELIVERED → COMPLETED`; alternate branches: `CANCEL_REQUESTED → CANCELLED`, `ON_HOLD`, `RETURN_REQUESTED → RETURNED`, `FAILED`. `COMPLETED` requires fulfillment/settlement policy checks; `DELIVERED` alone does NOT mean payment settled.
**Payment:** `PENDING → AWAITING_VERIFICATION / AUTHORIZED → CAPTURED / FAILED / EXPIRED`; `CAPTURED → PARTIALLY_REFUNDED / REFUNDED`; COD represented as unpaid collection receivable until evidence/reconciliation.
**Reservation:** `HELD → CONSUMED` at dispatch; `HELD → RELEASED / EXPIRED` for unfulfilled cancellation. Always atomically settle inventory ledger.
**Factory job:** `QUEUED → ACCEPTED → STOCK_CONFIRMED → PICKING → PACKING → PACKED → READY_FOR_HANDOVER → HANDED_OVER`, with `BLOCKED`, `PARTIAL`, `REJECTED` reason branches.
**Shipment:** `DRAFT → LABELLED → PICKED_UP → IN_TRANSIT → DELIVERED` or `DELIVERY_FAILED → RETURN_TO_SENDER → RETURNED`, with proof and timestamps.
**Quote:** `REQUESTED → IN_REVIEW → OFFERED → ACCEPTED → CONVERTED_TO_ORDER`, or `REJECTED / EXPIRED / WITHDRAWN`.
**Return:** `REQUESTED → UNDER_REVIEW → APPROVED / REJECTED → RECEIVED / REPLACED / REFUNDED → CLOSED`.
**Wholesaler:** `SUBMITTED → UNDER_REVIEW → APPROVED / REJECTED / NEEDS_INFO`, with explicit scope and tiers.

Each transition validates role, ownership, predecessor state, quantity/lots/region/payment guard and reason code; emits audit+outbox. Define transition table in code and test invalid transitions (409/422), including retry duplication.

## 09. REST API v1 — implementation contracts
**Common rules:** `https://api.<domain>/v1`, typed DTOs, OpenAPI, consistent `{data,meta}` success and `{code,message,details,requestId}` errors, UTC timestamps and Asia/Ho_Chi_Minh display, server-generated IDs. Customer routes use session/cookie or bearer architecture with CSRF protection where needed; secure HttpOnly cookies for web sessions preferred. All write operations have validation; financial and order mutations require idempotency and audit. Pagination cursor/page with limits. Public endpoints never expose costs or private documents.

**Public catalog/content**
- GET `/v1/categories`, GET `/v1/products?category=&search=&sort=&page=&limit=`, GET `/v1/products/:slug`, GET `/v1/variants/:id/availability`, GET `/v1/content/banners`, GET `/v1/content/policies/:key`, GET `/v1/content/articles[/:slug]`.

## 11. Critical algorithms, transactions and nonfunctional requirements
**Checkout reservation example pseudocode (design, not production SQL):**
```
BEGIN TRANSACTION;
  verify idempotency key and request hash;
  verify quote still valid and reprice all lines;
  for each SKU in deterministic order:
    atomic conditional UPDATE inventory_balances
      SET reserved = reserved + requested
      WHERE warehouse_id=? AND variant_id=?
        AND (on_hand - reserved - quarantined) >= requested;
    require exactly one row updated; else rollback OUT_OF_STOCK;
  INSERT order, order_items snapshots, payment PENDING, reservations,
         state_event, idempotency_response, outbox_event;
COMMIT;
```
If no physical stock: await supply or quote; never create fictitious reservation. For multi-warehouse/split fulfillment, document allocation and rollback strategy first. Expiry release job uses lock/unique guard to avoid release-after-dispatch. Multi-request concurrency tests must run against real PostgreSQL, not sqlite mocks.

**Security:** no hardcoded secrets, hashed passwords Argon2id, OTP secret hashed TTL, login/checkout rate limiting, session rotation, CSRF/cookie/CORS/HSTS security, strict file MIME/size scanning, signed uploads with private bucket, authorization on every query, SQL parameterization, XSS escaping, audit without logging OTP/tokens/PII unnecessarily. Restrict admin privileges and enforce MFA. Protect webhook signature, amount/currency/order/provider ref and event id; store provider raw event safely without secrets.

**Performance/SEO:** no fixed promises until measured; target Core Web Vitals/INP/LCP/CLS improvements, image optimization and pagination. API query index plans, cache only public data where safe. Monitor DB slow queries, queue depth, failed webhook, factory SLA, hold age, stock negative, COD mismatch. Health/liveness, structured logs trace `requestId`, queue/dead-letter retry, offsite backup and restore UAT.

**Legal/review gate:** BRD contains legal references and dates; do not treat this as legal certification. Verify obligations for sale site/app, seller information, privacy, data retention/deletion, food labeling, product compliance, invoices and tax with responsible advisers before launch. No fake registered-logo or payment compliance claims.

**Required UAT/E2E cases (automate where possible):**
1. Two customers order last available unit concurrently: exactly one succeeds.

3. Double-click/retry order: single order/hold/notification.
4. Duplicate/payment-webhook replay: one CAPTURE/ledger event; wrong amount must quarantine and alert.
5. Customer A opens customer B order; wholesale org A requests org B tier → denied.

11. COD delivered but unremitted remains outstanding and does not inflate settled cash.
12. Prior order margin does not change when list cost/price changes today.
13. Quote expires before acceptance; approval limits enforced; unapproved wholesale user sees no tier.
14. Return/refund without proof/permission rejected; audited authorized refund changes finance correctly.
15. OTP brute force/rate limit, reset token one-use, logout revokes session, privileged MFA.
